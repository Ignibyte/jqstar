# Migrating to jQStar 1.0

jQStar 1.0 keeps the 0.1 root behavior and stabilizes the modular, testing, CSP, Turbo, and htmx
entries that were labeled 0.4 previews. This guide covers the package changes. The roadmap release
numbers describe development tracks and are not a claim that each number was published to npm.

## Before changing the dependency

1. Record the installed `jquery-star`, jQuery, Node, Turbo, and htmx versions.
2. Find imports from `jquery-star`, declared subpaths, private `src/` paths, copied bundles, and CDN
   URLs.
3. Inventory `data-*` expressions, named actions, backend actions, plugins, registry components, and
   server response types.
4. Run the application with JavaScript disabled and record the native links, forms, validation,
   focus, and error behavior that must remain.
5. Add a focused browser test before changing root ownership, expression mode, or an external
   renderer.

The supported package ranges are Node `>=24`, npm `>=11` for release tooling, and application-owned
`jquery >=4.0.0 <5`.

## Install 1.0

Update the dependency and keep jQuery explicit:

```json
{
  "dependencies": {
    "jquery": "^4.0.0",
    "jquery-star": "^1.0.0"
  }
}
```

Run a clean install. Do not copy `dist/` files from the repository or import private source paths.
The package export map is the supported boundary.

## Choose the root or modular entries

The root import preserves 0.1 behavior. It imports jQuery, installs immediately, and composes core,
the Datastar protocol profile, and UI:

```js
import "jquery-star";
```

Use explicit modular installation when the application owns the jQuery instance or needs a smaller
graph:

```js
import $ from "jquery";
import { installStarCore } from "jquery-star/core";
import { datastarPlugin } from "jquery-star/datastar";
import { uiPlugin } from "jquery-star/ui";

const installed = installStarCore($);
installed.star.use([datastarPlugin, uiPlugin]);
```

The stable subpaths are `core`, `ui`, `datastar`, `csp`, `testing`, `datastar/testing`, `turbo`, and
`htmx`, plus `ui.css`. Only the root has an import-time side effect and UMD global.

The npm tarball contains the user-facing component, backend, CSP, interoperability, ecosystem,
migration, compatibility, security, support, and release guides. Contributor research and the
detailed CSP threat-model worksheet remain in the source repository rather than the installed
package.

## Request and server behavior

The root still selects `core.datastar` by default. It sends the documented Datastar headers and
signal encoding, then accepts JSON signal patches, HTML patches, Datastar event streams, and empty
responses. A modular core installation that does not install the Datastar plugin must select the
generic JSON/HTML profile explicitly.

Datastar streams must be produced by `@starfederation/datastar-sdk`. Applications should not copy
handwritten SSE strings from old examples. Existing HTTP authentication, authorization, CSRF,
validation, redirect, and retry rules remain application-owned.

## Lifecycle and disposal

Version 1.0 enforces one kernel and canonical jQuery instance per live document. If an application
previously loaded multiple package copies, consolidate them before upgrading. Use the public
terminal cleanup path:

```js
const report = $.star.dispose();
```

Destroy application roots before removing their DOM when an external renderer cannot use the render
adapter. Use `data-jqs-preserve` only for a live root deliberately retained through a patch. Wait
for `whenEnhanced()` before reading a completed incoming document state.

## Plugins, actions, and directives

The npm version is `1.0.0`; `STAR_PLUGIN_API_VERSION` remains `0.1.0`. Existing plugins should keep
an `apiVersion` range compatible with `0.1.0`. Installers are synchronous and transactional. Move
generic reusable behavior into a plugin registrar and keep application orchestration in registry
blocks.

Public extension directives use the installing plugin namespace. Helpers use dotted paths below that
namespace. Do not depend on private kernel maps, registry snapshots, or source file paths.

## Registry components

`jqstar add` continues to copy native HTML and block TypeScript into the application. Those files
remain application-owned after installation. Review local modifications before refreshing a block.
Component roots use `data-jqs`, stable internal slots use `data-part`, and reflected state uses
documented state attributes.

## Testing entries

`jquery-star/testing` is now stable. Supply the Window, Document, and jQuery realm explicitly. Its
response controller has no network passthrough. `jquery-star/datastar/testing` adds event-stream
fixtures generated by the official SDK. QUnit remains a tested consumer, not a runtime dependency.

Remove test imports from repository source paths. Install and test the exact package tarball when a
plugin or build integration depends on export maps, types, CommonJS, or browser behavior.

## Trusted expressions and CSP

The root entry retains trusted JavaScript expressions and their `unsafe-eval` policy requirement.
This is intentionally unchanged from 0.1. To use a finite expression language, install the CSP entry
explicitly:

```js
import $ from "jquery";
import { installStarCSP } from "jquery-star/csp";

installStarCSP($);
```

The CSP grammar is not JavaScript. Audit every expression against `jqstar-csp-expression/1`, move
unavailable operations into registered actions or helpers, and deploy the documented policy before
switching. Trusted server markup and trusted installed extensions remain required.

## Turbo and htmx

The bridge imports are inert until installed. Inject the host and exact version:

```js
import $ from "jquery";
import { installStarCore } from "jquery-star/core";
import { createTurboBridge } from "jquery-star/turbo";

const installed = installStarCore($);
installed.star.use(createTurboBridge({ $, Turbo, version: "8.0.23" }));
```

```js
import $ from "jquery";
import { installStarCore } from "jquery-star/core";
import { createHtmxBridge } from "jquery-star/htmx";

const installed = installStarCore($);
installed.star.use(createHtmxBridge({ $, htmx, version: htmx.version }));
```

Turbo support is `>=8.0.21 <8.1.0`; htmx support is `>=2.0.0 <2.1.0`. The host still owns requests,
redirects, caching, history, focus, forms, and DOM mutation. jQStar owns only its render transaction
and enhancement lifecycle.

## Naming

Use jQStar for the product, `jquery-star` for npm, `jqstar` for the command and repository, and
`data-jqs` in markup. jQStar is independent. It is not an official jQuery or OpenJS project and does
not claim to be a successor to jQuery UI or jQuery Mobile.

## jQuery UI and jQuery Mobile

jQuery UI can coexist in explicitly owned legacy islands while components move to native HTML and
jQStar one semantic behavior at a time. There is no Widget Factory adapter. Follow
`docs/JQUERY_UI_MIGRATION.md` for cleanup, focus, theme, and rollback boundaries.

jQuery Mobile migration is route by route. Modern routes are complete server documents using native
links and forms, responsive CSS, jQuery 4, and optional local jQStar enhancement. The Mobile page
container, Ajax router, roles, virtual controls, transitions, theme, and icons are not reproduced.
Follow `docs/JQUERY_MOBILE_MIGRATION.md`.

## What remains unchanged

- `$` is real jQuery and `$name` is a signal.
- Root installation and the default Datastar profile remain compatible with the 0.1 baseline.
- Server-rendered HTML remains the authority.
- Native links, forms, validation, focus, and errors remain the fallback.
- The plugin API and CSP grammar keep their independent versions.
- Application security and data ownership stay with the application.

## Final application check

Run unit tests, the supported three-browser matrix, a JavaScript-disabled pass, CSP tests when that
entry is selected, and an installed-tarball test. Verify that disposal releases the document and
that no private path, jQuery UI runtime, or jQuery Mobile runtime enters the production graph.
