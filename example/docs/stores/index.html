Shared stores

The optional jquery-star/stores plugin gives applications in one document a shared reactive namespace while keeping every root's local signals independent.

Authority boundary: stores are inspectable client coordination state. Never put secrets in them or use them for authentication, authorization, tenancy, durable persistence, or authoritative entity caching.

Choose the right owner

  • Use $name when one application root owns the value.
  • Use stores.name when several roots coordinate temporary client state.
  • Use an explicit storage adapter for durable browser preferences.
  • Keep permissions, validation, records, and server-state resources on the server.

Install and define a store

The stores entry is side-effect-free. Install it before the first application starts, then define stores either before or after roots mount.

main.ts 
import $ from "jquery";
import { installStarCore } from "jquery-star/core";
import { defineStore, storesPlugin } from "jquery-star/stores";

const installed = installStarCore($);
const shared = installed.star.use(storesPlugin);

const sessionDefinition = defineStore({
  initial: {
    count: 0,
    increment() {
      this.count += 1;
    },
  },
});

const session = shared.define("session", sessionDefinition);

A definition object owns one lower-camel ASCII name for the kernel lifetime. Repeating the same definition and name returns the existing reactive store. A different definition, another name for the same definition, or redefinition after publication fails.

Use shared and local state together

counter.html 
<section data-signals="{ store: 'local' }">
  <button data-on:click="stores.session.count++">Increment shared</button>
  <output data-text="stores.session && stores.session.count"></output>
  <output data-text="$store"></output>
</section>

$store always means the current root's local signal named store. The fixed stores root is the read-only shared namespace in trusted and CSP expressions. Without the plugin it is undefined, not an ambient global. The CSP grammar permits safe data writes below a store name; call named actions instead of store methods when using CSP expressions.

Accepted values and transactions

Store data accepts finite primitives, arrays, plain or null-prototype records, and ordinary function leaves. jQStar clones the caller's acyclic graph and preserves shared references. It rejects cycles, accessors, symbol keys, promises, DOM values, class instances, dates, maps, sets, and other live objects before publication.

Function leaves keep their identity and normal member-call this. jQStar does not bind, serialize, inspect by invocation, or register them as actions. Writes cannot add, remove, or replace a method.

restore.ts 
shared.transaction<typeof session>("session", (draft) => {
  draft.count = 10;
});

A transaction edits a detached validated draft and commits all data before one reactive flush. A throw, thenable, invalid graph, or method change leaves the live store unchanged.

Subscribe and own setup work

subscribe(name, selector, listener, options) compares selections with Object.is by default. Use { immediate: true } for the initial value and call the returned idempotent release function to stop. Batched writes deliver one later selection; one listener failure is observed without stopping siblings.

A definition's synchronous setup callback receives a frozen context with the store, its lifetime AbortSignal, and owned cleanup, effect, subscribe, and finite task helpers. Failed setup releases registered work in reverse order and never publishes the name. Kernel disposal makes the facade and stores terminal, aborts tasks, and attempts every cleanup once. Destroying one application stops its own store-dependent effects without removing the shared store or affecting another root.

Read the complete API, name and graph limits, observation metadata, and lifecycle details in the packaged stores contract.
